# WHAT REACHED THE BROWSER

**A device knows which browser it is.** Brave, Edge, Opera and Vivaldi all send a
Chrome user agent, so the detection that read only the string called every one of
them Chrome. The dashboard then showed the same word on every card, and a person
with two browsers could not tell which card was which.

The worker now believes what the browser publishes about itself before it reads
the string: `navigator.brave`, then the brand list in `userAgentData`, then the
string as the last resort. The page's own copy answers the same, and a test runs
both over the same browsers and fails when they disagree. The heartbeat carries
the name, so the chip corrects itself every thirty seconds instead of staying
whatever it was at pairing time. A new device takes its browser's name rather
than a number, so the list reads "brave" and "chrome" instead of "opera-4".

# WHAT REACHED THE SERVER

**"Cabut device ini" now looks like it worked.** The revoke cut the token and
set the row offline, but the account's device list carried every row, so the
card stayed on the page after the button and the reader concluded that nothing
had happened. The audit trail shows the revokes themselves ran; only the list
kept lying.

The revoke writes a state of its own now. The device list leaves that state out,
the relay never picks it, and the two devices revoked before this state are
marked the same way so they leave with the rest. The row stays in the table for
the history, and pairing the same browser again brings it back, which is what
the button has always promised.

**The dashboard counts presence, not a stored flag.** A device row keeps the
status it was last written with, so a browser that died two days ago still read
"online" and the dashboard counted three ghosts as daring. Presence is now the
same question the relay asks: has this device been seen inside the window the
extension's heartbeat lives in. A device the owner disabled is never live, and
never counted as one.

# WHAT THIS RELEASE COULD NOT HAVE SHIPPED WITHOUT

**The pin decides which browser answers.** The hosted road answered one call
against whichever browser was freshest at that millisecond. Tab ids live inside
one browser, so a chain that started on the everyday profile and continued on
another left the agent holding a tab id that existed on neither, and the failure
read as a broken tool. The pinned device answers every call while it is live,
and a pin that names a sleeping browser is refused by name, with the awake
browsers and the header that reaches one. `X-Opera-Device: any` is the caller
asking for the freshest browser on purpose.
