# WHAT REACHED THE SURFACE

**The hosted MCP surface loses `read_page_map` and gains nothing by losing it.** One tool now answers two questions. `read_page` (the default, `view: "brief"`) reads one viewport at a time: the task-facing observation with reusable refs and the delta since the last read. `view: "map"` reads the whole document the same way `read_page_map` did - every element in seventeen classes with document coordinates, the skeleton when no `class` is given, or one class paginated.

Same engine underneath: the extension already treated both as `page.read` with `view: "compact" | "map"`. This release takes the second surface away instead of pretending there were ever two.

**39 tools now, not 40** — the tool count is asserted in CI as frozen inventory; the number moves with reviewed decisions only.

**Everything reads 1.6.47.** Extension, npm package, update manifest, store listing, `SERVER_VERSION`, root and local `package.json`, the site's expected-version row - all follow the same number.

# WHAT CHANGED FOR CALLERS

- **Breaking for `read_page_map` directly:** callers naming `read_page_map` get "tool not found". Replace with `read_page` and `view: "map"`. The input fields and the output shape are identical to the old `read_page_map`.
- **New `view` field on `read_page`:** `brief` (default) and `map`. The parameters of both are merged into one schema; `class`, `all` and map-style `limit` apply when `view: "map"`, otherwise `includeElements`/`maxElements` apply.
- The pinned hosted inventory check (`tests/mcp-surface.test.mjs`) asserts 39 registrations, the fixture contract carries `toolCount: 39`, and the `sourceSha256` re-froze.

# WHAT IT COSTS THE READER

Nothing about the browser build changed except the number. The extension is byte-identical in behaviour to 1.6.46; the update path is the same: restart the browser and the registry/update flow delivers the new number.
