# WHAT REACHED THE BROWSER

The extension is unchanged in this release. What shipped is the **local driver** — the
MCP server that drives the everyday signed-in Chrome — and every change in it came
from a measurement taken on this machine against a real Google Docs document.

# WHAT WAS MEASURED, AND WAS WRONG

The local driver carried a claim in three places, including the comment at the top of
`window-focus.js`: *with the browser window behind another window, clicking and typing
go nowhere*. Measured on 2026-10-15, driving a Docs document:

| state | the page says | typed text |
| --- | --- | --- |
| browser behind another application | focus, visible | **landed** |
| browser minimized, caret in place | no focus, hidden | **went nowhere** |
| background tab of a front window | no focus, hidden | **landed** |

A window that is behind is not the problem. A window that is on the taskbar is. And a
background tab and a minimized window report *the same thing* to the page, so the page
cannot choose between them — only the operating system can.

# WHAT CHANGED

1. **An input action checks the window itself.** The page is asked first, because that
   is one evaluation and it gets the behind-another-app case right. The machine is
   asked only when the page says it is deaf, and only a window that is minimized is
   brought back. Every input answer carries one line: `the page hears input`, `brought
   <window> back from the taskbar`, or why it could not.
2. **`browser_status` stopped lying.** It answered `focused: true` with Brave in front
   while the drive was on a Chrome tab, because it asked whether *any* browser was in
   front and this machine has three. It now names the browser in front, and `focused`
   means the window holding a tab of ours.
3. **`type` proves the text landed.** It asks the page what it holds before and after —
   the body's length and tail, and the focused field's value — and fails when neither
   moved, naming which of the two facts it found. `stream_keys` reports whether the page
   moved instead of judging it, because a shortcut in a stream can move a page without
   the text ever landing.
4. **`focus_window` answers from one shell launch instead of two**, and reports which
   windows are minimized. Measured 5100 ms → 481 ms.
5. **A tab may be named.** `tabId` that is not a number is looked for by title or
   address; a name that fits two tabs is refused with both candidates. Every answer
   that hit a named tab carries that tab.
6. **A click marker takes itself off the page.** It never did, so a red ring sat on the
   page for the rest of the session and appeared in every later capture — including the
   one an agent reads its own click out of.
7. **The published package carried seven of the sixteen modules it imports.** `npx
   opera-local` would have installed a package that dies on its first import. The file
   list is now derived from the import graph, and a test compares them.

# WHAT A LOOP COSTS ON THE HEAVIEST REAL PAGE

Measured over the bridge against a Docs canvas: `click` 160 ms, `press_key` 205 ms,
`ax_snapshot` 19 ms, `capture_page` 349 ms, `find_elements` 14 ms, `browser_status`
476 ms, `read_page` 713 ms, `caret_line` 1171 ms. The last two are slow because they
carry the truth: each puts the caret back and reads the canvas.

# WHAT THIS RELEASE COULD NOT HAVE SHIPPED WITHOUT

The measurements above. The window check, the landing check and the marker cleanup all
exist because a real document produced a wrong answer that a screenshot showed and no
test had asked about.
