# WHAT REACHED THE BROWSER

The device's event emits are now chained instead of fired independently.

The streaming channel shipped in 1.6.23, and the first live run of it on a real
burst showed the defect that only a real run could show. The events arrived, in
the right kinds, with plausible timestamps — and `done` had been written at
1918ms while a step it was supposed to follow landed at 1921ms and another at
2175ms.

The cause is that each emit was an independent, un-awaited request. The burst
loop calls `onStep` and moves on, so the last step's request was still in flight
when `done` was sent, and two concurrent requests to the same bridge have no
guaranteed order between them. A consumer that trusted the order would have seen
a command finish and then keep receiving work.

Fixing it without giving up the property that made it cheap: the emits now chain
onto a single resolved promise. Ordering is preserved, and nothing in the burst
loop waits on the network — which was the whole reason the emit was never
awaited in the first place.

A test locks it, and the test bites: reverting to the independent emit fails it,
restoring the chain passes it.

# WHAT THIS RELEASE COULD NOT HAVE SHIPPED WITHOUT

A latency measurement that was measuring the wrong thing.

After the streaming release deployed, an 8-second round trip appeared. The
reading was alarming enough to look like the streaming transport had made the
product ten times slower. It had not.

The number came from timing a tool call from the outside, but the earlier
baseline had been read from the function's own internal timing — a different
clock, reporting a different thing — so comparing the two compared nothing.
Running the same measurement with the streaming transport turned off produced
the same nine and a half seconds, which is the only reason it was identified as
pre-existing rather than shipped as a fix for a bug that was never there.

The bridge answers the same request directly in 0.77 to 1.28 seconds, so the
delay sits in the relay used to reach the MCP function, not in the product's
runtime. The streaming transport costs nothing measurable: with it off the
median was 9448ms, with it on 9835ms, which is noise on a relay that already
dominates.

Worth recording because the mistake was not a careless one. It was a precise
number, from a real tool, taken the same way the baseline had been taken, and
it was still the wrong number.
