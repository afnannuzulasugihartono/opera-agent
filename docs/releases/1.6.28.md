# WHAT REACHED THE BROWSER

A 32nd primitive, `page.files`, and a 35th MCP tool, `upload_file`. Both carry bytes the
caller already has — base64 in the call — and put a real `File` on the page. Nothing is
read from the device's disk, and no native picker is opened.

The capability existed since the burst `file` step, but only inside a burst: `worker/burst.js`
was the one caller of `page.set_files`, so no tool, no method and no second path could
reach it. This release lifts it to a method and adds the road Google Drive needs.

# WHY TWO ROADS AND NOT ONE

| the page has | what the primitive does | how it is proved |
| --- | --- | --- |
| `<input type="file">` | sets `input.files`, fires `input` and `change` | the page reports `name:size` |
| only a drop zone (Drive, Docs) | builds a `DataTransfer` and dispatches `dragenter`, `dragover`, `drop` at `x, y` | the page reports `name:size:type` |

A drop zone reads `dataTransfer.files`; an upload button opens a picker no page can answer.
So the caller chooses by naming a point, and a target that is not a file input is refused
with the sentence that says how to drop instead — measured, not assumed: a `div` accepts
`div.files = …` silently and reported success before the check existed.

# WHAT THE WIRE REFUSES

`page.files` takes a `data:` URL, not base64, so the type travels with the bytes and there
is no second field to disagree with them. The MCP tool builds that URL from `upload_file`'s
`data` and `mime`, guessing the type from the filename when the caller does not say. The cap
is 2,000,000 characters, the same constant the burst step uses, so the two roads cannot
drift apart. Unknown parameters are refused rather than ignored, and a point needs both
coordinates.

# WHAT WAS DRIVEN, AND WHERE

In Chromium 156 with this extension loaded, on a page with one file input and one drop zone:

- `page.files` with `filename: catatan.txt`, 20 bytes → `mode: input`, `files: 1`, and the
  page's own `onchange` wrote `catatan.txt:20`.
- `page.files` with `filename: opera-agent-paper.docx`, 21 bytes, and the drop zone's centre
  → `mode: drop`, `target: div#dropzone`, all three events `prevented: true`, and the page's
  own `drop` handler wrote
  `opera-agent-paper.docx:21:application/vnd.openxmlformats-officedocument.wordprocessingml.document`.
- `page.files` with `selector: #dropzone` → `ok: false`,
  `No file input on this page. Give x and y to drop the file on a drop zone instead.`

The suite carries the same three cases in `tests/browser_extension_test.py` (the third
asserts the refusal), and `tests/protocol.test.mjs` holds the wire shape. Over the device
socket in that suite, the set took **5.3 ms** and the drop **43.8 ms** end to end; the drop
carries three events and a page handler, which is why it is the slower of the two.

# WHAT THIS RELEASE DOES NOT DO

- **No deploy.** The edge function, the landing pages and the CRX are dispatched from CI;
  this branch changes the source they are built from.
- **`page.read` still hangs on a Docs canvas**, and that is untouched here.
- **The cloud path still has no file-upload primitive of its own.** It reaches this one
  through the device, which is the design: the device holds the browser, the caller holds
  the bytes.

# WHAT THIS RELEASE COULD NOT HAVE SHIPPED WITHOUT

The measurements of the command queue on 2026-10-27: `tabs.list` 181–240 ms,
`browser.ping` 355 ms, `page.key` 291 ms, and a device that listed 31 capabilities with no
file primitive among them. That list is why this exists.
