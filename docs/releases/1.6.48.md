# WHAT REACHED THE SURFACE

**Every provider can now be bound to one browser, once, from any agent.** The hosted relay resolves the browser for a call in this order: the `X-Opera-Device` header on the call (that call only) > the provider pin stored for (your account, your `X-Opera-Provider`) > the freshest awake browser. Before this release the answer was "the header, else the freshest awake" - which meant a multi-harness setup (OpenCode + Claude + Codex over the same account) could not say "OpenCode drives Brave, Claude drives Chrome" without editing every client's config and restarting it.

**The pin lives in `opera_provider_pins`** (migration `20261112010000_opera_provider_pins.sql`; `user_id` + `provider` primary key; RLS on; no policies - the service role reads it, nothing else can). The pin names one browser: while it is awake it answers every call from that provider; when it is not, the relay answers `503 pinned_device_not_live` naming the silence, the awake browsers, and the way out (`switch_device` for provider pins, the header for header pins) - never a silent switch to a different browser.

**New tool `switch_device` (40 tools now, not 39)** - the tool count is asserted in CI as frozen inventory; the number moves with reviewed decisions only:

- `switch_device` with no arguments: read the current pin, the caller's provider, and the browsers awake right now.
- `switch_device({ device: "opera-8" })`: pin this provider to that browser for every later call. The name must exist on the account; a sleeping browser is accepted and reported as asleep, and calls are refused by name until it is awake.
- `switch_device({ device: "any" })`: clear the pin; the freshest awake browser answers (the pre-1.6.48 default).
- A call that writes `X-Opera-Device` always wins for that call - the pin is the default, the header is the override.
- Static tokens report `static_pin`; callers with an unidentifiable provider report `unknown_provider` (a pin is stored per provider, so the provider must be nameable).

**Everything reads 1.6.48.** Extension, npm package, update manifest, store listing, `SERVER_VERSION`, root and local `package.json`, the site's expected-version row - all follow the same number.

# WHAT CHANGED FOR CALLERS

- **No behaviour change for an existing caller.** A caller with no pin and no header gets exactly the freshest-awake routing it got in 1.6.47. A caller with a header gets the header, unchanged.
- **`browser_status` answers `pinSource`** (`header` | `provider` | null) beside `pinned`, so a caller can see why it landed where it did.
- **Breaking:** none for tools already in the surface; the inventory moved from 39 to 40 in the frozen fixture, `tests/mcp-surface.test.mjs`, and the landing/docs pages together.

# DEPLOY NOTES

- The migration was applied to production via the Supabase MCP before the code shipped; the table is additive and empty by default, so the relay behaves exactly as before until the first `switch_device` call.
- The edge function must be redeployed from `main` for the tool to exist; `deploy-functions.yml` is dispatched by hand. The CRX and npm package ship the new `SERVER_VERSION` through their usual paths.
